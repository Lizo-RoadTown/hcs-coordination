## Why it matters

- **`tapestry deploy` removes a manual, error-prone step.** Per the #175 commit message, hand-wiring a new Render service was "the most-repeated deploy chore." A stdlib-only, dry-run-capable CLI turns that into a scriptable, reviewable action — directly relevant to Tapestry's stated goal of standing alone as the system-of-record without ad hoc per-repo ceremony.
- **The auth probe fix closes a real, dated failure mode, not a hypothetical one.** The commit message states this blind spot "hid the Aug-2026 loom-memory outage for weeks" — i.e., CORE DIRECTIVE 1 (loom-memory reachability is mandatory) was silently unenforced whenever the token was bad but the host was up. `_check_auth` now escalates a 401/403 to the CONCRETE-RULE violation path, naming the fix (env-ref token, not a literal JWT).
- **Docs (#179, #180) followed the code same-session**, not as a backlog item — `how-to/deploy-a-service.md` and `reference/cli-commands.md` landed the same day as the features they describe, and ADR 0005 records *why* an imperative CLI coexists with the declarative `render.yaml` Blueprint rather than replacing it.

## Diagnosis (drift, risks, things to verify)

- **Snapshot tool blind spot, not a repo problem.** `integrations/claude-code/tapestry-patterns/scripts/architecture_snapshot.py:103` (`parse_render_yaml`) reads only `repo_root / "render.yaml"`. The actual file is at `infra/deploy/render.yaml` (confirmed present). Every snapshot this pipeline produces will report `render.present: false` and never show Render services/databases until this path is fixed or the file is symlinked/moved. This means the "Render services" dimension the analyst is meant to track has been silently blind since whenever `render.yaml` moved into `infra/deploy/`.
- **No committed `deploy/render-service.json` spec yet.** The CLI supports either a committed spec file or flags (per #175); a repo-wide search found none checked in. Not a defect — flags-only usage is valid — but if the intent was "spec file is the normal path," no repo currently demonstrates it.
- **`docs/architecture/UMBRELLA.md` was not touched in this range** (last modified at `901d300`, well before this session). The new CLI deploy capability is a genuine new operator-facing surface; worth a one-line check on whether UMBRELLA.md's canonical model should mention it, or whether that's deliberately out of UMBRELLA's scope (it documents system architecture, not CLI surface).
- **The snapshot pipeline ran on a stale checkout.** The 06:09 snapshot's `git_sha` (`d4e7388`) is 4 commits behind what was actually on `main` by the time this report was requested (`8648f21`). If this is the automatic SessionStart snapshot, the session that triggered it started before the later PRs merged — expected, not a bug — but it means anyone reading only `diff.json` for "what changed" will miss same-day work. That's exactly what happened here.
